# Streak Field Studio

Studio lives in Payload under **Assets > Streak Fields**. The plugin is registered in `src/plugins/index.ts`.

## Editorial workflow

A Streak Field is used like a media file. A visual slot holds the field, the site shows what is published, and editing happens in Studio. There are no versions to pick and nothing to re-pin: publish the field and every place that uses it shows the result.

**From a page (the usual way).** In any visual slot (hero, block, tab, menu preview) choose Streak Field. The slot has one picker: the shipped looks, **New field**, and "Use a field made in Studio".

1. **New field** creates a field named after the page and the slot ("About · Hero"), starting from the shipped look the slot shows now, and opens Studio in a drawer at that slot's placement. The page stays open behind it.
2. Tune it, then **Publish**. The two posters render in your browser in a few seconds and the field is published with them in the same request. Close the drawer: the slot shows the poster and the title.
3. Later, **Edit field** opens the same drawer. Tune, Publish, done: the page updates by itself, with no second publish. **Change** goes back to the picker.
4. With a field of your own in the slot, seed, speed and intensity are hidden: those belong to Studio, where the poster is rendered from the same numbers. They still adjust a shipped look, which has no editor. Pointer and the poster override stay.
5. A page cannot be published while its slot holds a field that was never published (the slot says so). Until then the page shows the slot's shipped look.

**In Studio (Assets > Streak Fields).** A field has a **draft**, which autosaves, and what is **published**. The header says where the draft stands ("Published, no changes", "Draft, 4 changes since published") and where the field is used. **Reset to published** puts what is on the site back in the draft. The Published list and the History tab hold every published state, from Payload's own versions: clicking one shows it on the stage beside the draft (looking never changes anything), Restore copies it into the draft. Reset and Restore are each one undo step, and neither changes the site until you publish.

- **Studio tab.** The stage shows the live field at a placement (hero, block, menu, card) on a dark or light ground, with a budget line under it (particles, DPR, octaves, segments; amber when the placement cap bites). Starters load a shipped look into the draft. Draft and Compare switch the stage between the draft and a comparison (a published state, or a draft you chose to Keep); any edit, undo or redo returns the stage to the draft. Seed and capture frame sit under the stage. Undo and redo hold fifty steps for the page (⌘Z, ⇧⌘Z). Space pauses, R randomizes the seed, C toggles the comparison while the stage has focus.
- **Inspector (sidebar).** Look, Pointer and Export tabs. On the Look tab every section starts closed, on every document, so the panel opens as a contents page: each header carries the section's summary and a dot when something in it departs from the default. The double chevron at the right of the tab strip opens or closes them all. Pointer is a single group, so its rows are flat, with Reset beside the note above them. Every numeric parameter is a slider row: label, a track with an always-visible thumb, and a value field. The label's tooltip carries the parameter's meaning, range, step and default; a dot, blue fill and a tick at the default mark a changed value; option-click the label to reset it, or Reset a group from its header. A row that needs another setting (Flow speed under Drift) shows muted with the reason and a one-click fix. Min and max length share one track with two thumbs that cannot cross; only the fields can, and the server's message shows under the row.
- **Publish** is disabled while the draft is what is published, and says "Publish to 3 places" when the field is shared. To take a shared field in a different direction for one page, duplicate it and point that page at the copy.
- **Details tab** holds title, description, tags, the two posters, archive, authorship and **Used on** (documents whose draft uses the field are marked). Edits there never touch the recipe.
- **Export** (Inspector tab) renders a PNG, WebP, or filled JPEG still in your browser: logical size, 1x or 2x scale, ground and alpha. It is filed in Media's Streak Field Studio folder and downloaded.

Archive hides a field from the picker; places that use it keep working. A field in use (by a document or its latest draft) cannot be deleted: remove it there first. The posters of a published field cannot be edited or deleted in Media; publish the field again to replace them.

**Restoring a page** works as it does for media. A page version stores the field's id, not its pixels, so a restored page shows the field as it is published today. The field's own history lives in Studio.

### Admin UI stack

The Studio components (`src/plugins/streak-studio/components`) are built from the site's shadcn primitives in `src/components/ui` (Slider, Tabs, ToggleGroup, Tooltip, Select, Input, Kbd) and Payload's own `Collapsible`, `Button`, `Link` and `toast`. Tailwind reaches the admin through one plugin-owned entry, `components/studio.css`: utilities only (no preflight), sourced from the primitives and the plugin, with the shadcn tokens painted from Payload's `--theme-*` scale so the Studio follows the admin's light and dark toggle. The token map, state variants and press recipe are shared with the site through `src/styles/shadcn-theme.css`. Nothing overrides Payload's own classes, every hook is a public `@payloadcms/ui` export, and components are registered by import-map path, so a Payload upgrade changes nothing here beyond what it changes for any custom field.

## Single source of truth

- `features/immersive/ui/streak-field-tuning.ts`: effect defaults.
- `features/immersive/studio/recipe.ts`: authorable parameters, validation, production envelope, capture limits.
- `features/immersive/visual/placement.ts`: existing placement ceilings.
- `features/immersive/visual/posters.ts`: page and menu poster resolution.
- `plugins/streak-studio`: the looks collection, authorization, publication, slot hydration, and admin UI.

Drafts store versioned deltas. Publish writes what the site renders from onto the look itself, the way image sizes ride on a media document: the resolved light and dark snapshot, the poster manifest, the two poster uploads and the hash of the published recipe (`snapshot`, `posters`, `thumbnail`, `lightPoster`, `sourceHash`; hidden, written only by Publish). A visual slot stores the look's id in `shader.studio`. `hydrateStudioFields` walks each document once, batches every nested slot per request, and replaces the id with the published look's `{ id, sourceHash, snapshot, posters }`, read from the published document and nothing else, since it lands in public page responses. A field that was never published keeps its bare id and the slot falls back to its shipped look. Public pages receive a compact descriptor, never the library or editor, and render through the existing poster-first lazy adapter and its admission, pause, visibility, reduced-motion, capability, and fallback behavior.

Identity is the snapshot. `recipeHash` (`plugins/streak-studio/hash.ts`) hashes the resolved snapshot in canonical, key-sorted form, because Postgres `jsonb` returns keys reordered and the editor keeps the order it built; "draft matches published" in the stage uses the same canonical comparison. A look can only be published with its posters: the `beforeChange` guard accepts the Publish endpoint's write (a request-context pass, handed over for that one write and taken back) or output that is already published (Payload's Revert to published), and nothing else.

The initial authoring envelope fixes strokes at one segment and caps noise octaves, count, DPR, and high-overdraw combinations. Count is the one resource number the Inspector may set (Composition, 100 to 8000): it is what density reads as, and its range stops at the hero ceiling, so a recipe can ask for less than code allows and never for more. Limits apply after creative overrides. Studio uses the same effective limits. This conservative envelope is a policy, not proof of 60 fps on every GPU; use the existing performance measurement runbook for target-device qualification. Software Chromium capture is not a real-device benchmark.

## Rendering

Stills render in the editor's browser. `captureStill` (`features/immersive/studio/capture.tsx`) mounts the shared `FieldScene` on its own offscreen canvas, advances fixed 1/60-second simulation steps with neutral pointer input, draws the final frame, reads PNG pixels and takes the canvas down. Intermediate visible draws are skipped; flow simulation steps still run. Output scale changes pixel resolution without changing the logical layout. The live preview pauses for the moment it takes, so the capture has the GPU to itself, and stills render one at a time.

`POST /api/streak-looks/:id/publish` takes the recipe and the two PNGs. In one transaction it locks the look, checks that the recipe it was sent is the saved draft (so the posters match the field), verifies each image is PNG at exactly the poster size, converts and files them in Media, and publishes the look with its snapshot and posters. `POST /api/streak-looks/:id/export` does the same for one still at the chosen size. Both are team-only (`authenticated`, never `Boolean(req.user)`). Nothing renders or encodes inside a visitor page request, and there is no queue, worker, lease or Chromium function: the poster comes from the GPU the editor previewed on.

Pixels vary slightly between GPUs and drivers; the generated files, not a promise of identical pixels, are authoritative. Renderer compatibility changes require a version bump; a published field whose renderer the site no longer supports falls back to its preserved posters. After such a bump, republish each field from Studio (a one-off local Playwright script can do it for a long list).

## Database and rollout

`20260917_220809_streak_field_studio` added looks with native versions, plus the earlier release and render tables. `20260919_000344_streak_field_as_media` moves to the media model: it adds `studio` to every visual slot and version table and the published fields to looks, points every slot that pinned a release at that release's look, and gives each look what its newest release carried, so the site renders the same pixels from the look from the first request on. It is additive. The `streak-releases` and `streak-renders` collections and the `release` column on every slot remain as bare, hidden schema that nothing reads; a follow-up migration drops them (pure removals, so `migrate:create` asks nothing). Local development uses Drizzle push; deployment CI applies the migrations. No migrations are applied to the local push-managed database.

Preview deployments run on their own Neon branch. The Neon deployment action on the Vercel store connection is enabled for `production` and `preview`, so each git preview deployment (the `preview` branch) gets a Neon branch named `preview/<git-branch>` forked from the production branch, and the branch connection variables are injected at deploy time (they are not stored in Vercel env settings). The build then runs `payload migrate` against that branch, so the production ledger only changes on `main` deploys. The stored connection variables still resolve to production for every environment (the Neon action only fires when they do), so `pnpm ci` runs `scripts/guard-preview-db.ts` first: a non-production build that sees the `PRODUCTION_DB_ENDPOINT` host, or no `POSTGRES_URL` at all, aborts before `payload migrate` instead of touching production. The Vercel-managed Neon project is not visible to the local Neon CLI; manage branches from the Vercel Storage tab (Open in Neon) or with a Neon org API key.

Placement-specific poster generation remains outside this workflow. A slot's crop can differ from the field's poster; use an exported still through the existing poster override when exact art direction matters.
