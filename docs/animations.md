## Route transitions

> **In flight:** navigation-experience overhaul tracked in [route-transitions-roadmap.md](route-transitions-roadmap.md) (audit 2026-08-31 — coverage gaps, default-transition redesign, edge-case policy).

- `DirectionalTransition` wraps every page via `src/app/(frontend)/template.tsx` and maps transition *types* to CSS classes. The default is a **mask reveal** (brand grammar — no page crossfades, see [route-transitions-roadmap.md](route-transitions-roadmap.md) §4): the old page holds static (`reveal-hold`) while the new page's snapshot clips open over it; `nav-forward` reveals from the right edge, `nav-back` from the left, `nav-lateral` top-down (the scroll-reveal wipe at page scale).
- Links tag their navigation: `CMSLink` takes `transitionDirection: 'forward' | 'back' | 'lateral'` (default `lateral`); raw `next/link` takes `transitionTypes={[...forwardNavTransitionTypes]}` from `@/shared/lib/view-transition`; `useClickableCard` tags its body-click push (`nav-forward` by default); the form block tags its confirmation redirect (`nav-lateral`).
- Untagged navigations (browser back/forward, revalidations, search-as-you-type URL sync, menu pushes) animate nothing — `default: 'none'`. **Tagging is not an opt-out from the transition itself.** React flags a view transition for any newly placed subtree containing a `<ViewTransition>`, and `(frontend)/template.tsx` remounts one on every route change, so `document.startViewTransition()` runs on every navigation; the classes only decide whether anything animates. A started transition suspends the document's rendering (and rAF) from its capture until React's update callback resolves — which React holds for up to 500ms on the incoming page's above-the-fold images and fonts. That freezes any imperative motion playing across the commit and, since GSAP's ticker only smooths gaps past 500ms, snaps it forward on the next tick. Navigations whose motion is owned imperatively (both menu paths — hero handoff and plain undock) therefore also call `suppressViewTransitions()` (`src/shared/lib/view-transition/suppress.ts`), which removes the API for the flight and puts React on its own no-transition commit path.
- All timing lives in the `:root` block of `view-transition.css` (`--vt-duration-*`, `--vt-ease-reveal`, `--vt-ease-hero`). The simulator's copy button emits exactly that block.
- Elements that must not cross-fade get their own named group and `animation: none` — the header, the footer, and the persistent WebGL canvas (`.vt-global-canvas`).
- **Work-media takeover** (`work-open`): "View case study" in `IndustryWork` is a plain `next/link` tagged with `workOpenTransitionTypes` — the fades and fallback glide are declared in `view-transition.css`; the only imperative piece is the beat split (below). The root maps `work-open` to dedicated `work-exit`/`work-enter` classes, and the `morph-hero` shared element (`workImageVtName`, block media ↔ case-study hero media) is delayed by `--vt-duration-exit` and fill-held at the spotlight's rect. Both sides type-gate their `share` (`workImageShare` in `shared/lib/view-transition/constants.ts` — `{ 'work-open': 'morph-hero', default: 'none' }`): the name pair also forms on navigations the takeover does not own (a menu hero-handoff push, browser back/forward) whenever the spotlight and hero coexist across the swap, and an ungated string `share` would play the CSS fallback glide over that navigation's motion. The post-image morph is gated the same way (`postImageShare`, forward/back only). The **approach** is two strict beats, each position-only or size-only: the old page fades out (and stays out — `both` fill) while the media glides straight up/down at the spotlight's size until it is vertically centered in the viewport, x untouched (`--vt-duration-hero-center`), then it expands about its own center until it covers the viewport (`--vt-duration-hero-expand`). Nothing moves or resizes after that — the expand's `forwards` fill pins the group full-screen and the shared **hero landing** finishes the navigation exactly as the menu handoff does: hold, the group's clip-path closing one axis at a time onto the hero's rect (uncovering the page around it), then the hero snapshot dissolving in. The incoming page fades in the moment the media reaches full screen (`work-enter` delays by exit + center + expand) — under the full-bleed media, invisible, so it is fully painted before the mask starts uncovering it. Movement beats ease with `--vt-ease-hero-travel` (strong in-out); the expand keeps `--vt-ease-hero`; the landing's own curves come from `HERO_LANDING`. There is no visible media swap — both sides render the same asset: the spotlight snapshot stays opaque for the whole flight and the hero snapshot only fades in at the end, pixel-identical where crops match and hiding the crop/resolution delta inside the dissolve where they don't (overriding both layers' `animation-name` also removes the UA fade + `plus-lighter` blend). The sequenced landing also lays the hero snapshot out at the hero's own rect inside the still-full-screen group rather than stretched across it — that snapshot is what the live page replaces frame for frame when the pseudo tree is dropped, so a stretched crop would pop. The beat split lives in `work-image-morph.ts` (`onShare` on the IndustryWork side cancels the browser's one-rect group tween and replaces it with the WAAPI beats, reading the `--vt-*` variables for the approach and the plan for the landing); if that bails (no group animation, reduced motion), the CSS single-rect glide over the approach's duration remains as fallback. Persistent chrome (header/footer/canvas) keeps its pinned named groups and never participates. Scroll correctness relies on `LenisRouteReset` (`SmoothScrollProvider`) resetting Lenis + scroll in a *layout* effect — inside the view transition's update callback, before the incoming page is snapshotted. Reduced motion, modified clicks, and browsers without view transitions degrade to plain navigation.

## Scroll reveal

- Wrap the section in `ScrollReveal` (from `@/shared/ui/scroll-reveal`) — or `src/blocks/case-study/RevealSection.client.tsx`, a thin wrapper that adds theme, viewport sizing, and the block's `variant` — and mark descendants:
  - `data-reveal` → text track (drop from above + blur settle, staggered in document order)
  - `data-reveal-group="<name>"` → optional, text track only: neighbouring targets sharing a value land on **one beat** instead of consecutive ones. Use it for a cluster the reader takes in as a single thought — an eyebrow and the heading it labels. Without it the kicker leads its own heading by a stagger step, and since the drop is a fixed px it is also the largest motion relative to its own type size, so the smallest element becomes the loudest one in the block. Grouping is positional (only neighbours collapse), so one group name repeated per list item still cascades. Markers stay on the elements, never a wrapper: `text-stack` spaces a cluster through direct-child selectors
  - `data-reveal="media"` → media track: the container acts as a clipped window and a top-origin mask wipes down — the wipe alone, no fade and no blur (both expensive on large media). `mediaScaleFrom` can additionally settle the first child down from a zoom behind the mask; it ships at `1`, and at `1` no scale is written at all (the transform would make that child a containing block for its absolutely-positioned media)
- The two tracks run independently, each on its own timeline. `stagger` spaces consecutive **beats** within a track (`revealStaggerSlots` resolves targets to beats, collapsing grouped neighbours); `mediaOffset` delays a track after **its own** gate (negative = copy waits `-mediaOffset` after the copy has entered, `0` = a track plays as soon as it has entered, positive = media waits after the media gate; ignored on shells with no media). Scroll-gated blocks leave it at `0`: the gates sequence a stack on their own (the image wipes when the image arrives, the copy drops in when the copy arrives, so the text entrance is never spent off-screen) and fire together side by side, landing a heading and the image it aligns with on one beat. An offset only earns its keep in shells whose targets all enter at once — a pin, or a shared `gateSelector` — where nothing else can order the tracks.
- **One variant per block, everywhere.** A block whose markup carries `data-reveal` markers maps to its reveal variant exactly once, in `src/blocks/shared/reveal-variants.ts`. Every renderer — Pages/Home (`RenderBlocks`), work (`RenderCaseStudyBlocks`), lab (`RenderLabBlocks`) — reads that map, so the same CMS block plays the same GSAP reveal on every surface; marker-less blocks take the CSS block reveal from their renderer instead. `'self'` blocks (statement links) mount their own shell and must never be wrapped in a second entrance — which is why the post body rich text (where statement links can be embedded) has no CSS reveal wrap.
- **Two reveals, each owned whole.** `SCROLL_REVEAL_INTRO` is the complete reveal for introduction / text-only blocks; `SCROLL_REVEAL_UNDER_MEDIA` is the complete reveal for copy paired with media (its own text tuning + the wipe + the sync offset). They share nothing but the trigger gate, so tuning one never moves the other. Blocks pick one with `variant="intro" | "underMedia"` via `RevealSection`; explicit props still win over the variant's values.
- Each track has one viewport gate; the entrance is **play-once** — the gate disconnects after it fires, so scrolling back past a revealed section never reverses or replays it (`SCROLL_REVEAL_EXIT_TIME_SCALE` now only speeds up click-driven swap exits). The gate measures **position, not visible fraction**: `observeRevealGate` fires when that track's own target has risen `SCROLL_REVEAL_TRIGGER_DEFAULTS.enterOffset` of the viewport past the fold. One number covers every block height — a ratio gate fired early on shells several screens tall (they can never expose a large fraction of themselves) and on shells whose copy sits at their bottom edge (the ratio fills from the wrong end), so the settle was over before the copy arrived. A single shell-wide gate on the first text target hid media-first layouts; a single gate on the image spent the copy's entrance off-screen. Bespoke shells (`WorkIntro`, `AudienceTabs`) call the same helper. Reduced motion renders the final state; server-rendered children stay visible without JS.
- A shell that cannot report its own scroll position — a sticky or fixed band is on screen from the first paint — passes `gateSelector` at an in-flow marker instead. The footer closing band is the one such surface (see **The closing curtain**).
- Never hand-roll a new reveal tween. If a shell needs different choreography (see `src/sections/WorkIntro/Section.client.tsx`), it still imports the shared gate (`SCROLL_REVEAL_TRIGGER_DEFAULTS`) and any value one of the reveals already owns (ease, durations, the intro stagger) instead of restating it.
- Audience tabs is a `'self'` block with a bespoke shell (`src/blocks/AudienceTabs/use-audience-tabs-motion.ts`): a phased entrance (heading → tab buttons → list items → media wipe last, media start computed from item count) and a swap whose text transition and image change start on the same click — the incoming image immediately wipes down over the outgoing one on an underlay (the outgoing image never animates, so the container background never shows) while the outgoing text fades out in place and the incoming text snaps in with a fast fade. Every shared value is imported from the reveals; only entrance phase offsets are owned locally. Its entrance targets overlap its swap targets — safe because the entrance is play-once and finishes before any swap can start.
- Dropdown-driven panel swaps (dynamic audience, industry work) use `useRevealSwap` from the same module: `data-swap="text"` / `data-swap="media"` targets fade in place (opacity only — no blur, no lift), then the incoming half fades in. Timings live in `SCROLL_REVEAL_SWAP` (under 250ms); the scroll entrance (`SCROLL_REVEAL_UNDER_MEDIA`) is never replayed. Industry work additionally crossfades media over the outgoing frame at click so the spotlight never empties, and keeps the WebGL canvas mounted (hidden only for the dissolve). Swap targets stay distinct nodes from the shell's `data-reveal` targets. The shared headline-with-dropdown line itself is `src/blocks/shared/heading-dropdown.tsx`.

## The closing curtain

The footer closing band (`src/Footer/Closing/`) is not scrolled to — it is **uncovered**. The band is `sticky bottom-0`, parked at the foot of the viewport from the first paint, and the page article above it (`relative z-10 bg-background`, set on every surface that renders the band) scrolls up off it. The reveal edge travels up the screen; nothing translates.

- **Where the numbers live.** `src/Footer/Closing/curtain.ts` owns the flow marker's selector. The band is pinned, so its own rect says nothing about scroll; a 1px marker (`-mb-px h-px`, its own height cancelled) sits at the band's flow position, and how far that marker has risen past the fold *is* how much of the band the page has uncovered. Both the reveal gate (`SCROLL_REVEAL_CURTAIN_ENTER_OFFSET`) and the background parallax scrub read it, so both are timed off one line.
- **One mask, not two.** The band's media carries no `data-reveal="media"` marker: the curtain already uncovers the whole screen from the bottom edge up, and the reveal's own top-down wipe over the same pixels reads as two edges fighting. The copy keeps the text track.
- **Sticky pins the margin box.** The band's `-mb-(--footer-height)` eats the page frame's footer padding, so the sticky offset is `bottom-(--footer-height)` — exactly that margin added back, or the band parks that far under the fold.
- **`tall:` only.** Pinning costs the band its own scrollability, so it holds only above the `tall` height breakpoint (`globals.css`, 44rem); shorter viewports keep the band in normal flow so a stack taller than the screen can still be scrolled through.
- **Pinned means always composited.** `LightLeak`'s own off-screen gate never fires on a pinned band, so `ClosingLightLeak` mounts it from the marker instead — otherwise the shader runs for the whole session behind an opaque article.
- **The leak follows the site theme.** The band is built from semantic tokens, so in light mode its ground is white — and an additive leak adds nothing to white. `ClosingLightLeak` reads `<html data-theme>` (`useSiteTheme`) and swaps in `LIGHT_LEAK_PAPER`, the absorptive cut of the same effect: it multiplies instead of screening, and the shader's composite flips to a dye layer over the page. A toggle changes uniforms and one CSS blend mode — the canvas is never remounted and the program is never relinked.

## The tuning workflow

1. Dial values in on the demo page — every parameter is wired to the section's GUI, with a replay button.
2. **Copy** emits code for the paste target shown in the guide (a `:root` CSS block, a `*_DEFAULTS` const, or component props).
3. Paste at the target. Every consumer reads from there — no call site restates a tuned value.

The Hero landing section is the tuning surface for `HERO_LANDING` — it plays the real plan on a mock viewport, so a value dialed there moves both the menu handoff and the work-open transition. The two scroll-reveal demo sections map 1:1 onto the two reveal consts — every value of a reveal is controlled in its section, and **Copy** emits the whole const, so a paste can never drop a key. Each section also plots a to-scale timeline diagram of every target's start, with an overlap/sequential readout. The trigger gate (`SCROLL_REVEAL_TRIGGER_DEFAULTS`) is live-tunable in both but not part of either copy snippet — transcribe it manually if you change it.

## Shared foundations

- **Smooth scroll.** Lenis runs site-wide in `root` mode from `SmoothScrollProvider` (`src/providers/`), advanced on the tempus clock so it shares RAF timing with WebGL. It persists across navigations, so `LenisRouteReset` returns it to the top (or the anchor) on every route change. Reduced motion skips the provider entirely and gets native scrolling.
- **Reduced motion.** Every JS system reads `usePrefersReducedMotion` (`src/hooks/`); CSS systems gate on `prefers-reduced-motion`.
- **Lenis is the only writer of the document scroll position.** Every programmatic scroll goes through `lenis.scrollTo` (`LenisRouteReset`, the menu's `restoreFrame` while the frame is out of Lenis's hands aside). ScrollTrigger features that move the page (the featured work roll's `snap`) would otherwise write `window.scrollTo` natively, and Lenis ignores native scroll events while its own ease is still running: the two alternate writes every frame at settle, Lenis stamps its stale position back when it completes, and the snap re-fires (a visible jump back and a second glide). `SmoothScrollProvider` registers a `ScrollTrigger.scrollerProxy` for the window that routes writes through `lenis.scrollTo({ immediate: true })` and reads natively; without a root Lenis (reduced motion) it is the native default. Never add a second scroll writer; route it through Lenis.
- **The chrome reads scroll through one subscription, and never while the page frame is docked.** `components/SiteChrome/chrome-scroll.ts` owns the chrome's only `scroll` listener: one `scrollY` read per event, fanned out to the bars' scrolled shrink (`useScrolledChrome`, run by the header) and the hero band's palette pin. Freezing the frame (`position: fixed` + html `overflow: hidden`) collapses the document, so `scrollY` snaps to 0 on the next frame; read as "back at the top" it would grow the bar from 3rem to 4rem mid-dock and move the preview slot the open timeline had just measured. So the subscription skips every event while `[data-page-frame][inert]` exists (dock through undock) and runs every subscriber once when `restoreFrame` drops the attribute, after the frame is back in flow at its final offset. That thaw dispatch is not optional: a menu-link navigation lands at 0 and the collapsed document was already at 0, so no scroll event follows and the shrunk state would otherwise stick on the new page's first screen.
- **Nothing measures itself while the page frame is docked.** The takeover menu freezes `[data-page-frame]` under a `scale(...)` for as long as it is open, and the route commits *inside* that transform (menu link → `router.push`, hero handoff). `getBoundingClientRect()` is transform-aware, so anything that sizes itself from it during the dock bakes in the dock's scale — and undocking clears only the transform, which fires no `ResizeObserver`, so nothing ever re-measures. R3F `<Canvas>` measures exactly that way: the home hero's lens came up at 0.6978x and stayed there, ending ~70% across its section with a hard edge. Every canvas therefore spreads `CANVAS_RESIZE` (`src/lib/webgl/canvas-resize.ts`) — react-use-measure's `offsetSize`, which reads the untransformed layout box. GSAP ScrollTrigger measures the same way and has no untransformed alternative: a scroll-driven effect mounted by a route that committed mid-dock (the featured work roll, the closing band's parallax) bakes in start/end positions from the scaled frame over a document collapsed to one viewport, so the trigger sits past its end once the real page scrolls (the roll pinned on its last item until a hard reload). `restoreFrame` (`Header/Menu/index.tsx`) therefore calls `ScrollTrigger.refresh()` once the frame is back in flow and the scroll offset is final. Any new measure-on-mount code owes the same care. `HeroBand`'s chrome pin measures its geometry only while the frame is live and re-measures from a `MutationObserver` on that attribute, which fires after `restoreFrame` has restored the scroll offset.
- **The fixed chrome follows the hero band under it, and nothing else sets it.** `HeroBand` (`src/heros/HeroBand.tsx`) is the root of every hero that paints its own palette: it stamps the section-level `data-theme` and, through the `ChromeThemeProvider` store (`src/providers/ChromeTheme`), pins the header and footer bars to the same palette (transparent plate, so the band's media runs under them) for exactly as long as each bar sits entirely over the band: the footer releases first, the header last, and a band that starts below the header's top edge (the medium-impact hero) pins the header only once it has scrolled fully under it, since a lifted plate over any sliver of page would carry the wrong ink. The pin is *derived*: the band caches its document-space edges and the bars' scrolled heights (`--header-bar-height-scrolled` / `--footer-bar-height-scrolled`, globals.css) and every scroll is a comparison against them, no layout read; resize, the band's own `ResizeObserver` and the frame's thaw refresh the cache. The store is external to React (`useSyncExternalStore`): a flip re-renders one bar shell (`HeaderBar`, `FooterBar`) and nothing else, and the band's unmount releases both, so a route change cannot strand a stale pin. The bars fade palette and plate together on their existing 300ms transition; their children inherit `color` so they ride the same fade instead of snapping. The header drops the pin while the takeover overlay is up, since it then reads against the overlay's site-theme surface. Pages never set the chrome theme: a page without a band has no writer.
- **`scroll-fade` utilities** (`globals.css`) mask the edges of a scroll container using `animation-timeline: scroll()`, with a static-mask fallback. Size via `--scroll-fade-size`; no JS involved.

## Scroll cost

Under Lenis every scroll is **time-based**: a long frame doesn't slow the page, it teleports it. Main-thread work on a scrolling frame therefore reads as stutter *and* skipping — and the reveals, which run exactly while the page is moving, are where it shows. Two rules hold that line.

- **Nothing forces layout in a scroll handler.** Lenis dispatches a scroll event on every frame it moves the page, so a handler that reads geometry (`getBoundingClientRect`, `elementFromPoint`, `checkVisibility`) pays a synchronous style + layout flush inside the scroll step of every scrolling frame — and during a reveal, the dirty tree it flushes is the entrance. Coalesce the work into one rAF per frame, and batch every read before any write: an inline style write between two reads makes the next read flush again, which is a layout pass per element instead of one per scan. The cursor's proximity scan (`src/features/cursor/CustomCursorProvider.tsx`) is the reference implementation of both halves.
- **Paint-bound tween properties get a `will-change` for the length of the tween, and only that long.** A `filter` blur or a `clip-path` wipe re-rasterizes its target on the main thread every frame unless the element is promoted. `ScrollReveal` hints each track with exactly what that track animates (`revealWillChange`), set on the timeline's `onStart` and released on its `onComplete` — a hint left on is a promoted layer held for the life of the page. Every hint spans a window in which the tween already applies that property, so it creates no stacking context or containing block the entrance didn't already have; `panel` targets stay off `filter` for the same reason their tween does (it would kill their `backdrop-filter`).

### Open follow-ups

- **Two RAF loops.** GSAP writes tweens on its own ticker while Lenis and R3F run on the tempus clock (`src/lib/interactions/smooth-scroll.tsx`), so the order of the scroll write and the tween writes inside a frame is not guaranteed. The fix is one loop: `gsap.ticker.remove(gsap.updateRoot)` + `gsap.ticker.lagSmoothing(0)`, then `gsap.updateRoot(time / 1000)` in the tempus callback after `lenis.raf(time)`. Not taken yet — it is global blast radius, and reduced motion skips the provider entirely, so the detach has to be scoped to the mounted `SmoothScroll` and restored on unmount.
- **Full-viewport wipes.** `will-change: clip-path` is a stacking-context hint, not a guaranteed compositing trigger in Chrome, so a full-screen `fullMedia` wipe may still repaint per frame. Adding `transform` to the media hint would force promotion, at the cost of making the media container a containing block for its absolutely-positioned descendants — the same trade `mediaScaleFrom` documents.

## Rules

- Every tunable number exists in exactly one place; consumers import, never restate (same contract as [immersive-effects.md](immersive-effects.md)).
- Reuse an existing system before adding a new one; a second usage of a custom tuning gets promoted to the shared source, not copied.
- `prefers-reduced-motion` collapses every system to its final state — any new motion must do the same.
- A scrolling frame has a budget: no forced layout in a scroll handler, no un-promoted paint-bound tween (see **Scroll cost**).
- Demo playgrounds (`src/widgets/transition-demo/`, `src/widgets/immersive-demo/`) are demo-only, never shipped UI.
