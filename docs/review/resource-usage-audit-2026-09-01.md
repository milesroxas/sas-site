# Vercel + Neon resource audit (2026-09-01)

Findings only — **nothing here has been applied.** Written to be picked up cold later.

Trigger: hitting Vercel and Neon limits with no public launch. The apex `suits-sandals.com` is still Webflow; this site serves from `preview.suits-sandals.com`.

**Headline:** rendering is fine — 36 routes prerender correctly, nothing is accidentally dynamic. The burn comes from four things stacked on top of a static site: an indexable preview domain feeding crawler traffic into a per-pageview API call, an image pipeline that routes every byte through a Payload function at `q=100`, and an uncached media CDN.

## What was verifiable

| | |
|---|---|
| Verified | Repo source, `node_modules` behaviour of Next/Payload/plugins, the committed `.next` production build (2026-08-27), live response headers from `preview.suits-sandals.com` and `media.suits-sandals.com`, GitHub Actions run history, prod media docs via the `sas-cms` MCP |
| **Not** verifiable | Vercel usage meters (`vercel whoami` → `Not authorized`; the Vercel MCP server is unauthenticated), Neon compute-hours dashboard |

So the findings are mechanism-and-evidence, not metered attribution. **Before acting, open Neon → Monitoring and read the compute-hours chart by hour** — a constant low-level floor points at crawlers, spiky points at builds. That single chart decides how much of this matters.

## Findings

### 1. Preview domain is open to every crawler — the amplifier

`preview.suits-sandals.com/robots.txt` explicitly welcomes 13 AI crawlers plus everything else, with only `/admin/*` disallowed, and no `X-Robots-Tag` header:

```
User-agent: GPTBot     Allow: /   Disallow: /admin/*
User-agent: CCBot      Allow: /   Disallow: /admin/*
User-agent: Amazonbot  Allow: /   Disallow: /admin/*
...
User-agent: *          Disallow: /admin/*
```

On an unlaunched staging origin, **bots are the traffic**, and every crawled page drags findings 2 and 3 behind it. Googlebot renders JS, so it also fires the `/api/users/me` call. Secondary problem: the staging domain gets indexed and will compete with the real site at launch.

Generated by [next-sitemap.config.cjs](../../next-sitemap.config.cjs) at `postbuild`.

**Fix** — gate on an explicit opt-in env var:

```js
const isProd = process.env.ALLOW_INDEXING === 'true'

robotsTxtOptions: {
  policies: isProd
    ? [...AI_CRAWLERS.map(...), { userAgent: '*', disallow: '/admin/*' }]
    : [{ userAgent: '*', disallow: '/' }],
  additionalSitemaps: isProd ? [...] : [],
}
```

Set `ALLOW_INDEXING=true` in Vercel only at cutover. **Do not key this on `VERCEL_ENV === 'production'`** — `preview.suits-sandals.com` may be the project's production alias, which would make that check a silent no-op.

Also worth disallowing `/api/` for `*`. Nothing good comes from a crawler walking the REST API.

### 2. `AdminBar` fires an uncached function call on every pageview

[src/app/(frontend)/layout.tsx:38](../../src/app/(frontend)/layout.tsx) renders `<AdminBar>` unconditionally. `@payloadcms/admin-bar` fires this in a `useEffect` with no guard:

```js
await fetch(`${cmsURL}/api/users/${authCollectionSlug}/me`, { credentials: 'include' })
```

Measured live:

```
GET /api/users/me → 200, 1.056s, x-vercel-cache: MISS
cache-control: public, max-age=0, must-revalidate
```

An otherwise-100%-static site pays **one uncached ~1s Payload function + Neon touch per visitor pageview**. Also keeps Neon compute awake whenever anyone — or any JS-rendering bot — is on the site.

Payload's `payload-token` cookie is httpOnly, so the client cannot self-gate.

**Fix (recommended)** — gate on draft mode:

```tsx
{isEnabled && <AdminBar adminBarProps={{ preview: isEnabled }} />}
```

*Verified safe:* `next/dist/server/request/draft-mode.js` only calls `trackDynamicDraftMode` from `enable()`/`disable()` — reading `.isEnabled` does **not** bail out of prerendering. The layout already calls `draftMode()` today while 36 routes prerender.

*Tradeoff:* the bar stops appearing for logged-in team members browsing outside preview. If that matters, the alternative is a non-httpOnly `payload-signed-in` companion cookie set from a Users `afterLogin`/`afterLogout` hook, with the client gating on `document.cookie`.

### 3. Image pipeline — four multipliers stacked

From the committed build, one home-page image:

```
sizes="200px"  → srcSet with 15 widths: 32…3840, every one at &q=100
src fallback   → w=3840&q=100
url            → /api/media/file/<file>?<updatedAt>
```

**3a — media served through a Payload function, not the CDN.** `s3Storage({ collections: { media: true } })` leaves Payload access control on, so `resource.url` is `/api/media/file/...`. Every image-optimizer cache miss is a Vercel Function invocation running `checkFileAccess` (a Neon query) + `headObject` + `getObject`, streaming the **full original** from R2 through the function. `@payloadcms/storage-s3/dist/getFile.js` sets only `Content-Type` and `ETag` — **no `Cache-Control`** — so the Vercel CDN never caches it. Meanwhile `VideoMedia` already goes direct to `NEXT_PUBLIC_MEDIA_URL`.

The `usageStatus` gate is not real protection here: R2 objects are already public on `media.suits-sandals.com` (see [.env.example](../../.env.example)). You are paying function cost for a gate that is already open.

**3b — `quality={100}` everywhere.** [ImageMedia:107](../../src/components/Media/ImageMedia/index.tsx) plus `qualities: [100]` in [next.config.ts:34](../../next.config.ts). 3–8× the bytes of `q=75` on both hops.

**3c — default `sizes` is invalid CSS.** [ImageMedia:87](../../src/components/Media/ImageMedia/index.tsx) builds `(max-width: 1920px) 3840w, …`. `3840w` is not a `<length>`. Next's `getWidths` only matches `vw` units; finding none it falls through to `widths: allSizes` — all 8 `deviceSizes` **plus** all 8 `imageSizes`. Same at [FeaturedCard.tsx:52](../../src/Home/hero/FeaturedCard.tsx) (`size="200px"`) and [Card/index.tsx:84](../../src/components/Card/index.tsx) (`size="256px"`).

**3d — cache-busting query.** `?updatedAt` invalidates every optimized variant whenever a media doc is touched.

Live optimizer behaviour: `cache-control: public, max-age=60`, but repeated fetches return `x-vercel-cache: HIT` at `age: 138` — so Vercel's edge honours its own `minimumCacheTTL` (4h default), while **browsers revalidate every 60s**. Net: origin re-fetch + re-billed transformation every ~4h per variant, × 8–16 widths per image.

**Fix — see [Correction C1](#c1--do-not-use-generatefileurl--disablepayloadaccesscontrol) below. The obvious approach breaks three things.**

### 4. Neon compute — the cron is *not* the cause

The GitHub Actions runner at [.github/workflows/payload-jobs.yml:25](../../.github/workflows/payload-jobs.yml) declares `*/10 * * * *` = 144 runs/day. **Actual run history says otherwise:**

```
scheduled runs/day:  16, 34, 22, 3, 2, 6, 7, 4, 6
                     Aug24 ......................... Sep1
```

~5/day for the past week. GitHub silently drops scheduled runs on free shared runners. So this costs ~12 Neon compute-h/mo, not the ~360 a real 10-minute cadence would. **Not a cost driver — leave it alone.**

Remaining candidates for whatever *is* waking Neon, unmeasured:

- `/api/users/me` per pageview (finding 2), fed by crawler traffic (finding 1)
- Vercel builds — `pnpm ci` runs `payload migrate` then prerenders 36 routes against prod Neon, with `depth: 4` on work pages. 127 commits in 30 days.
- Local work against remote: `dev:tui` prod mode, `migrate:status`, and the `sas-cms` MCP `find*` tools all target production
- ISR regeneration on the 3600s floor (finding 6)

> **Separate bug, not a cost issue.** `schedulePublish: true` is on **12 collections**, and the queue only drains when this workflow fires. A post scheduled for 09:00 currently publishes somewhere between 09:00 and ~14:00; observed gaps on Sep 1 were 2h38m–5h30m. The `0 6 * * *` cron in [vercel.json](../../vercel.json) is the only dependable trigger — once a day. Crashed newsletter-send recovery has the same latency. Fixing it needs a scheduler that honours the interval (Vercel Pro crons, or an external pinger). **Lower Neon's autosuspend to 1 minute first** — restoring a true 144 wakes/day at the 5-minute default really would cost ~360 compute-h/mo.

### 5. Telemetry proxies — real at scale, not yet

`/ingest/*` and `/monitoring` compile to **external rewrites** (verified in `.next/routes-manifest.json` — absolute destinations in `afterFiles`), so Vercel proxies them at the routing layer with no Function invocation. But every event is a billed **Edge Request + Fast Data Transfer both ways**.

PostHog runs `defaults: '2025-05-24'` → autocapture (every click), pageview, pageleave, web vitals, exception capture. Easily 20–50 requests/session, plus the JS bundle pulled through `/ingest/static/*`. Sentry tunnels every envelope at `tracesSampleRate: 0.2`. GA4 and Vercel Speed Insights run alongside — four telemetry pipelines.

If Edge Requests turns out to be the meter: disable `autocapture`, load PostHog's JS from its own CDN instead of proxying, drop `tunnelRoute` unless ad-blocked Sentry data matters, lower `tracesSampleRate` to `0.05`.

### 6. `revalidate: 3600` leaks onto every route

[getMenuContent.ts:136](../../src/Header/getMenuContent.ts) sets `revalidate: 3600` on the `unstable_cache`. `Header` renders in the `(frontend)` root layout, so **every route inherits it** — confirmed in `.next/prerender-manifest.json`:

```
3600  /            3600  /works/adacore     3600  /who-we-help/…
600   /posts       600   /works             600   /insights/*
```

~36 routes × 24 = **~860 ISR renders/day** under continuous traffic, each a function invocation + Payload boot + Neon queries (`/works/[slug]` runs at `depth: 4`).

**Do not simply delete these — see [Correction C3](#c3--the-revalidate-windows-are-load-bearing).**

### 7. Minor

- `maxDuration = 300` at [route.ts:16](<../../src/app/(payload)/api/[...slug]/route.ts>) applies to the **whole** Payload REST surface, including `/api/users/me` and `/api/media/file/*`, not just newsletter sends.
- The jobs workflow swallows curl exit 28 (240s timeout) as success, so a run that hangs to the 300s `maxDuration` is invisible.
- `public/robots.txt` is committed with `Host: http://localhost:3001`. `next-sitemap` overwrites it at `postbuild` so prod is fine, but the committed artifact is misleading — gitignore it.
- `PAYLOAD_DB_PUSH` is absent from prod env. **Not a problem** — `@payloadcms/db-vercel-postgres/dist/connect.js` gates `pushDevSchema` on `NODE_ENV !== 'production'`. No action.

## Corrections — approaches that look right and are not

A second pass against the Payload source and this repo's own wiring invalidated three of the obvious fixes. **Read this section before touching anything.**

### C1 — Do not use `generateFileURL` / `disablePayloadAccessControl`

`@payloadcms/plugin-cloud-storage/dist/hooks/afterRead.js` shows `generateFileURL` takes precedence over everything and rewrites `url` **globally, on every read, for every consumer**:

```js
if (generateFileURL) { url = await generateFileURL({ collection, filename, prefix, size }) }
else if (disablePayloadAccessControl && adapter.generateURL) { ... }
```

Three things break when `media.url` becomes absolute:

1. [generateMeta.ts:27](../../src/utilities/generateMeta.ts) does `serverUrl + image.url`, assuming relative. Absolute input yields `https://preview.suits-sandals.com/https://media.suits-sandals.com/…` — **every OG image dies.**
2. [webglMediaSrc.ts:16](../../src/utilities/webglMediaSrc.ts) matches `/^https?:\/\//` in its first branch and would return CDN URLs for WebGL textures; it deliberately routes through the same-origin proxy. Consumers: [HeroBackground](../../src/Home/hero/HeroBackground.tsx), [IndustryWork](../../src/blocks/IndustryWork/Component.client.tsx), [scroll-gallery](../../src/blocks/scroll-gallery/Component.client.tsx).
3. `disablePayloadAccessControl: true` additionally strips `adapter.staticHandler` from `upload.handlers` (`plugin.js:73`), deleting `/api/media/file/*` outright — which `webglMediaSrc` and [demo-media.ts:9](../../src/shared/ui/demo-kit/demo-media.ts) reference by construction.

**Instead — change only `ImageMedia`, mirroring the pattern `VideoMedia` already proves in production:**

```tsx
// src/components/Media/ImageMedia/index.tsx
const cacheTag = resource.updatedAt
src = cdnSrc(resource.filename, cacheTag) || getMediaUrl(url, cacheTag) || undefined
```

Verified against prod data via `findMedia`: R2 keys are **flat** — `filename` and every `sizes.*.filename` are siblings with no prefix — so `${MEDIA_URL}/${filename}` resolves for originals and renditions alike. `media.url` stays relative, so `generateMeta`, `webglMediaSrc`, the newsletter's `absoluteUrl()`, and the admin panel are untouched. Local dev with `NEXT_PUBLIC_MEDIA_URL` unset falls back to the proxy.

### C2 — The R2 CDN is not cached and sends no `Cache-Control`

Assumed the Cache Rule was live. It is not. Repeated live probe:

```
GET https://media.suits-sandals.com/interchecks-laptop-home-feature-section.webp
cf-cache-status: DYNAMIC      ← both fetches, never cached
(no cache-control header at all)
```

Flipping `ImageMedia` to the CDN removes the Vercel Function from the image path, but the optimizer still gets no cache directive and browsers still get `max-age=60`.

**Add the Cloudflare Cache Rule on `media.suits-sandals.com` first** — Eligible for cache, Edge TTL + Browser TTL 1 year. Safe because `?updatedAt` versions the URL and Payload writes a new filename on re-upload. *Then* flip `ImageMedia`. Order matters.

Unrelated but noted: R2 **does** send CORS today — `access-control-allow-origin: https://preview.suits-sandals.com` with `vary: Origin`. The comment in `webglMediaSrc.ts` claiming otherwise is **stale**. Leave the code alone, but if textures ever move to the CDN, add the production origin to the R2 CORS policy first.

### C3 — The `revalidate` windows are load-bearing

They are not redundant with the on-publish hooks. Traced:

- `revalidatePost` purges `/posts/<slug>` and `/posts` **only** — not `/insights`, not `/insights/[topic]`, not `/posts/page/[n]`, not `/post`. Those pages list the same posts.
- [Capabilities.ts](../../src/collections/Capabilities.ts) and [Industries.ts](../../src/collections/Industries.ts) have **no hooks at all**, and `/works` renders their names as browse filters.
- `takeover-menu-content` is invalidated only by `revalidateHeader`, but `getMenuContent` reads `expertise-pages`, `audience-pages`, `work-pages`, and `pages`.

Deleting the windows freezes all of that until an unrelated global is republished.

**Instead — one line, most of the win:**

```ts
// src/Header/getMenuContent.ts:136
revalidate: 86400,   // was 3600
```

That floor propagates to every route, cutting whole-site ISR regeneration **24×** while leaving a 24h backstop. Leave the explicit `revalidate = 600` on index pages until the missing purges are added — a separate, careful change.

### C4 — Dropped: trimming `deviceSizes`

Once `sizes` carries real `vw` units, Next filters `allSizes` to `>= deviceSizes[0] * smallestRatio` and the tiny `imageSizes` fall out on their own. Removing `3840` would cost visible quality on full-bleed 4K hero images for little extra gain. Not worth it.
